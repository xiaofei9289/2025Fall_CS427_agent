# Four-arm retrieval/tool ablation — 2026-10-19

Status: **one 10-task round; retrieval tools were not used in the plain retrieval arm, so this is not a tool-effect result.**

## Design

- Source: main `39c1833` / frozen digest `bd68cb05e5e6`
- Tasks: first 10 of `verified50_tasks.json` (includes `matplotlib-20826`)
- 400 steps, $10/task, 2 workers, official SWE-bench grading
- Arms:
  - A `baseline_tool`: file tools only
  - B `brief_tool`: + deterministic `repo_brief`
  - C `retrieval_tool`: brief + `code_search` / `repo_map` / `code_context` / `find_references` + action prompt
  - D `gate_tool`: legacy forced-first-search gate + `code_search` / `repo_map`

## Results

| Arm | Resolved | Cost | API calls | Retrieval tool calls |
| --- | ---: | ---: | ---: | ---: |
| A baseline | 8/10 | $0.1023 | 217 | 0 |
| B brief | 8/10 | $0.0806 | 201 | 0 |
| C retrieval | 9/10 | $0.0499 | 139 | **0** |
| D gate | 9/10 | $0.1014 | 268 | **10** (`repo_map` 5, `code_search` 5) |

- All 10 tasks completed; no empty patches, no grading errors.
- A failed `django-11532`, `sympy-13615`.
- B failed `django-11532`, `matplotlib-20826`.
- C/D failed only `django-11532`.
- The +1 for C/D over A is one task, single round; not statistically meaningful.
- **C never called any retrieval tool** (0 `code_search`, `repo_map`, `code_context`, `find_references`). Its 9/10 cannot be attributed to retrieval tools; it used the brief/action prompt or run noise.
- D forced `repo_map`/`code_search` and matched C at 9/10, but cost 2x and used 268 calls vs 139. No evidence that forcing search improved resolution.

## Decision

Per the pre-registered rule: if the retrieval arm makes 0 retrieval calls, stop and fix the tool exposure before another round. Do not run round 2 of the same config and do not report a tool effect.

Next options:

1. Make retrieval tools actually used (tool descriptions/instructions, or treat the gate as the treatment).
2. If using the gate as treatment, run gate vs baseline for 2 rounds and report it as a package effect.
3. Keep brief/action-prompt changes separate from tool availability.

## 250-step cap and stronger retrieval prompt (2026-10-19)

The four configs were lowered from 400 to **250** steps and `retrieval.yaml` got an
explicit "make at least one retrieval-tool call before the first edit" instruction.
The existing four-arm calls peaked at 91, so 250 does not bind for A/B/D; their
400-step results remain valid under 250. Focused re-runs:

| Run | Resolved | Cost | Calls | Retrieval tool calls |
| --- | ---: | ---: | ---: | ---: |
| retrieval 3-task smoke | 2/3 | $0.0100 | 35 | 1 (`code_context`) |
| retrieval 10-task recheck | 9/10 | $0.0730 | 192 | 2 (`code_context`) |

- The 10-task recheck still failed only `django-11532`; all 10 completed, no empty/errors.
- The new prompt only moved **2/10** tasks to call a retrieval tool; the rest solved with
  file tools. `code_search` / `repo_map` / `find_references` were still unused.
- Resolved count is unchanged at 9/10 vs the 0-call run; no evidence of tool gain.
- 250 steps did not change any outcome: all runs stayed far below the cap (max 40 in the
  recheck, 91 in the earlier gate run).

### Updated decision

The cap change is validated but the treatment is still mostly inactive. Do not run a
50-task version and do not claim a tool effect. The next step, if any, must be a stronger
treatment (engine-level tool gate or a deliberately constrained tool-only arm), not a
larger sample of the current retrieval prompt.
